# Task: StreamFlow SignalR Optimization with .NET Channels

## Description

Replace ConcurrentDictionary-based message queueing in StreamFlow with bounded .NET Channels for better throughput, proper queue semantics, and backpressure handling. This optimization targets the real-time messaging system to handle high-volume message flows efficiently.

## Current Implementation Issues

**File: `StreamFlow.Core/Interfaces/ICachingService.cs`**
- Uses `ConcurrentDictionary<Guid, StreamFlowMessage> QueuedMessages` - lacks proper queue semantics
- Uses `ConcurrentDictionary<Guid, TaskCompletionSource<StreamFlowMessage>> PendingMethodCalls` - no backpressure

**File: `StreamFlow.Stream/Services/Handlers/Events/PushMessageHandler.cs`**
- Uses `goto` statements for retry logic (lines 58-62, 71-82) - inefficient
- No backpressure handling - messages can overwhelm system
- Manual queue depth checks (line 112) - not thread-safe under high load
- `Console.WriteLine` instead of structured logging

**File: `StreamFlow.Stream/Services/Handlers/Events/RegisterClientHandler.cs`**
- Uses `goto` for random key generation (lines 20-29) - poor practice

## Implementation Notes

### Channel Configuration
```csharp
var options = new BoundedChannelOptions(10000) // Capacity
{
    FullMode = BoundedChannelFullMode.Wait, // Apply backpressure
    SingleReader = true,  // StreamFlowProcessor is single reader
    SingleWriter = false  // Multiple SignalR connections write
};
```

### Expected Performance Improvements
- **20-30% better throughput** under high load
- **Proper backpressure** prevents memory exhaustion
- **Better CPU utilization** - channels are optimized for producer/consumer patterns
- **Thread-safe queue semantics** - no manual locking needed

### Migration Strategy
1. Create new Channel-based infrastructure
2. Update handlers to use channels
3. Test with existing SignalR clients (no client changes needed)
4. Remove old ConcurrentDictionary-based queueing
5. Verify performance improvements with load testing
